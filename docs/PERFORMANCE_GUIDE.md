# Performance Optimization Guide

Данный документ описывает архитектурные и технические решения, позволившие достичь высокой производительности при обработке больших объемов финансовых данных (150,000+ строк).

## 1. Hot-Loop Optimization

Основная нагрузка при парсинге файлов приходится на цикл обработки строк. В этой области были проведены следующие оптимизации:

### Устранение регулярных выражений в циклах
Ранее для очистки данных использовался `re.sub` внутри каждой итерации. Это создавало значительные накладные расходы на компиляцию и выполнение regex.
- **Решение**: Регулярные выражения теперь предварительно компилируются (`RE_NUMERIC_CLEAN`), а наиболее частые операции (удаление пробелов) выполняются через высокопроизводительный метод `str.translate` с использованием таблицы трансляции.

### Оптимизация CalamineReader
Вместо последовательного сканирования всех ячеек, `CalamineReader` теперь:
- Выполняет "быстрый проход" (первые 6000 строк) для определения структуры заголовков.
- Использует кэшированные наборы ключевых слов (`aliases_lower_list`) для сопоставления колонок.
- Минимизирует преобразования типов, выполняя их только для колонок, имеющих финансовое значение.

## 2. Pydantic model_construct

Pydantic — мощный инструмент, но его стандартная валидация (`__init__`) слишком медленна для "горячих циклов" (миллионы вызовов).

### Как это работает
Метод `model_construct()` создает экземпляр модели **без запуска валидаторов**.
- **Ускорение**: В 10-20 раз быстрее стандартного создания объекта.
- **Когда использовать**: Когда данные уже очищены и валидированы на предыдущем этапе (например, внутри ридера).

### Ограничения
- **Отсутствие валидации**: Если в данных ошибка типа, она проявится только при использовании объекта.
- **Обязательные поля**: Вы должны передать все поля, иначе объект будет неконсистентным.
- **Значения по умолчанию**: Если поле пропущено в аргументах `model_construct`, оно может не получить значение по умолчанию из схемы.

> **Note**: В текущей реализации для достижения экстремальной производительности (<1.5с) в критическом пути используются сырые словари (`dict`), что устраняет накладные расходы даже на `model_construct`.

## 3. Producer-Consumer SQLite

Запись в базу данных часто является узким местом из-за блокировок диска (I/O).

### Архитектура
Реализован паттерн "Производитель-Потребитель":
1. **Producer**: Потоки обработки файлов (`FileProcessor`) подготавливают данные и помещают их в `queue.Queue`.
2. **Consumer**: Выделенный фоновый поток (`DBWriterThread`) вычитывает очередь и выполняет запись.

### Преимущества
- **Изоляция I/O**: Запись в БД не тормозит парсинг файлов.
- **Пакетная обработка**: Данные записываются через `executemany`, что критически важно для SQLite.
- **PRAGMA Оптимизации**:
    - `synchronous = OFF`: Огромное ускорение за счет отказа от ожидания подтверждения записи на диск ОС.
    - `journal_mode = WAL`: Позволяет читать данные, пока идет запись.
    - `cache_size = -64000`: Увеличение кэша в памяти (64MB).

## 4. Multi-file Parallelism

Обработка файлов распараллелена на уровне `AppController` с использованием `ThreadPoolExecutor`.

- **Стратегия**: Каждый файл обрабатывается в отдельном потоке. Это идеально подходит для сетевых дисков, так как задержки сети при чтении файла A перекрываются вычислениями файла B.
- **Скейлинг**: Количество воркеров динамически определяется на основе `os.cpu_count()`.

## 6. Рекомендации по масштабированию

Для настройки производительности под конкретное железо используйте параметр `max_workers` в `AppController`:

- **Сетевые диски (Низкая задержка)**: Рекомендуется `max_workers = CPU_COUNT * 2`.
- **Медленные сетевые шары**: Можно увеличить до `32-64`, чтобы скрыть задержки I/O.
- **Локальные SSD**: Рекомендуется `max_workers = CPU_COUNT`, так как узким местом станет CPU, а не диск.
