## 1. Роль ИИ-исполнителя

ИИ должен работать как ведущий инженер по качеству и надёжности desktop-приложения с финансовыми данными. Цель — не переписать программу, а доказуемо улучшить существующую рабочую систему без изменения подтверждённых бизнес-правил.

Основной принцип:

> Сначала зафиксировать правильный результат, затем менять инфраструктуру вокруг него. Любое изменение финансового результата без отдельного согласования владельца считается дефектом.

ИИ обязан:

1. Работать по этапам этого ТЗ строго по порядку зависимостей.
2. Перед изменением изучать существующий код, тесты и документацию соответствующего модуля.
3. Не смешивать рефакторинг, изменение поведения и массовое форматирование в одной задаче.
4. Добавлять или изменять тест одновременно с исправлением дефекта.
5. После каждого этапа запускать предусмотренный gate и сохранять результат проверки.
6. Не объявлять этап завершённым при наличии падений, необъяснённых skips или расхождений.
7. Не пушить, не публиковать релиз и не менять рабочие компьютеры без явного разрешения владельца.
8. Не выводить в чат, логи, отчёты или Git реальные имена сотрудников, суммы, токены и содержимое рабочих Excel.
9. При необходимости изменить бизнес-правило остановиться и запросить решение владельца с примерами последствий.
10. Сохранять обратную совместимость с существующими `config.yaml`, `employees.yaml`, SQLite и рабочими книгами.

- отдельная ветка вида `hardening/<номер>-<краткое-название>`;

## Этап 0. Заморозка baseline и исправление инфраструктуры проверки

### Цель

Получить воспроизводимую точку отсчёта и исключить ложные зелёные проверки.

#### MR-0001. Зафиксировать окружение

- Установить `requirements.txt` и `requirements-dev.txt` в чистую `.venv`.

- Нормализовать пути и номера строк единообразно локально и в CI.
- Блокировать только новые ошибки относительно baseline на переходном этапе.

#### MR-0004. Единый источник версии

- Устранить расхождения 5.5/5.6 в GUI, BAT, логах, диагностике и документации.

#### MR-0005. Синхронизировать runtime и development проверки

- Не обязательно менять текущую структуру веток немедленно; обязательно исключить публикацию непроверенного runtime-кода.

#### MR-0006. Тайминг baseline и аудит секрета

- Измерить и зафиксировать в baseline-отчёте длительность ключевых операций (старт приложения, refresh сотрудников, консолидация контрольной даты). Без этих чисел этап 8 не сможет считать regression threshold.

### Gate этапа 0


Критерии:

- 0 failed и 0 errors;
- все skips классифицированы;

## Этап 2. Версионирование и миграция конфигурации

### Цель

Любая новая версия должна принимать старую рабочую конфигурацию без ручного редактирования и тихой потери настроек.

#### MR-0201. Схема конфигурации

- Добавить `config_version`.
- Описать конфигурацию типизированной схемой Pydantic.
- Разделить ошибки: отсутствующее поле, неправильный тип, недоступный путь, неизвестное поле.
- Не считать временно недоступный сетевой путь синтаксически невалидной конфигурацией.

#### MR-0202. Последовательные миграции

Создать модуль миграций вида:

```text
APP/core/config_migrations/
├── __init__.py
├── v1_to_v2.py
```

Требования:

- миграции последовательные и идемпотентные;

- запись идёт во временный файл с атомарной заменой;
- после миграции схема полностью валидируется;
- при ошибке исходный файл восстанавливается;

## Этап 3. Надёжность чтения Excel и качество данных

### Цель

Повреждённый, раздутый, заблокированный или нестандартный файл не должен приводить к зависанию приложения, тихой потере строк или сбою обработки остальных сотрудников.

### Задачи

#### MR-0301. Изоляция парсера

- Установить явные timeout для потенциально зависающих операций.
- Опасные операции python-calamine выполнять изолированно там, где подтверждён риск падения нативного кода.
- При падении calamine использовать контролируемый fallback, если он не меняет семантику.
- Нельзя бесконечно повторять один и тот же повреждённый файл.

#### MR-0302. Повреждённые и раздутые книги

Тесты минимум для:

- неверной ZIP-сигнатуры `.xlsx`;
- обрезанного архива;
- workbook без нужных XML;
- листа с used range до 1 048 576 строк;
- большого числа пустых форматированных строк;
- скрытых листов;
- формул без cached value;
- защищённой книги;
- файла, открытого в Excel;
- временного `~$` файла.

#### MR-0303. Валидация дат

- Формализовать допустимые форматы названий листов.
- Даты без года обрабатывать по действующему бизнес-правилу.
- Добавить предупреждение о слишком далёком прошлом/будущем.
- Подозрительная дата не должна молча попадать в обычную массовую сборку без видимого предупреждения.

#### MR-0304. Журнал потерь данных

Для каждой пропущенной строки фиксировать обезличенную причину:

- файл/лист через безопасный идентификатор;
- номер строки;
- код причины;
- стадия обработки;
- severity;
- операция/session ID.

Не писать полные финансовые значения и персональные данные.

#### MR-0305. Частичный успех

- Ошибка одного сотрудника не отменяет корректные результаты остальных, если бизнес-правила разрешают partial result.
- UI показывает число успешных, пропущенных и ошибочных источников.
- Финальный статус различает `completed`, `completed_with_warnings`, `failed`, `cancelled`.

### Gate этапа 3

- Ни один повреждённый fixture не завершает весь процесс аварийно.
- Нет зависаний дольше установленного timeout.
- Все пропуски отражены предупреждением/журналом.
- Golden-набор этапа 1 остаётся без изменений.

```text
│   ├── cache.db
│   └── runtime_state.json
├── logs/
└── backups/
```

Допускается адаптация структуры при наличии доказанной несовместимости, но код версий и пользовательские данные должны быть физически разделены.

### Задачи

#### MR-0401. Bootstrap updater

- BAT остаётся тонкой стабильной точкой входа.
- Updater не должен зависеть от файлов версии, которую он в этот момент заменяет.
- Поддержать Windows PowerShell 5.1 либо явно включить необходимый runtime в поставку.
- Не требовать прав администратора для обычного обновления.

#### MR-0402. Lock и preflight

- Глобальная блокировка второго экземпляра updater.
- Проверка запущенного приложения.
- Проверка прав записи и свободного места.
- Проверка доступности текущей версии.
- При недоступном обновлении предложить запуск текущей версии.

#### MR-0403. Staging и атомарное переключение

- Новая версия полностью готовится в `.staging`.
- Зависимости устанавливаются/готовятся внутри staging, не поверх рабочей среды.
- Выполняется self-check.
- Только после успеха меняется указатель текущей версии.
- Старые удалённые модули не переносятся в новую версию.
- Хранятся минимум две предыдущие рабочие версии.

#### MR-0404. Self-check

Без механизмов защиты реализовать:

- L0: структура файлов, версия, размер, SHA-256 архива;
- L1: импорты, bootstrap, конфигурация, тестовая копия БД, ресурсы GUI;
- L2: маленькая синтетическая консолидация во временном каталоге с golden-сравнением.

Self-check не имеет права читать/изменять реальные отчёты, кроме безопасной проверки существования настроенных путей.

#### MR-0405. Startup confirmation и rollback

- Новая версия после запуска создаёт сигнал `startup-ok` с version/session ID.
- Updater ждёт ограниченное время.
- При отсутствии сигнала автоматически возвращает предыдущий указатель.
- Ошибка миграции конфигурации или БД также вызывает rollback.
- Rollback не удаляет диагностические логи неудачной версии.

#### MR-0406. Offline ZIP

- Один и тот же update engine принимает GitHub-источник и локальный ZIP.
- Offline ZIP проходит те же L0–L2 проверки.
- Нельзя распаковывать абсолютные пути и `..` за каталог staging.
- Нельзя ставить версию с несовместимой схемой без мигратора.

#### MR-0407. Тестовая матрица updater

Автоматизировать минимум:

- нет интернета;
- HTTP 401/403/404/429/500;
- повреждённый/обрезанный ZIP;
- неверный SHA-256;
- недостаточно места;
- каталог read-only;
- приложение запущено;
- двойной клик updater;
- путь с пробелами и кириллицей;
- установка без `.git`;
- удалённый в новой версии модуль;
- отказ установки зависимостей;
- отказ config/DB migration;
- новая версия не выдаёт `startup-ok`;
- повторная установка той же версии;
- попытка downgrade;
- прерывание каждого шага с проверкой восстановления.

По возможности добавить локальный test-source, чтобы интеграционные тесты updater не зависели от GitHub.

### Gate этапа 4

- Ни один тест updater не повреждает текущую версию или `data/`.
- При любом отказе текущая версия запускается.
- Offline ZIP работает без интернета.
- Удалённые модули не остаются.
- После успешного обновления L2 golden совпадает.
- Сотруднику достаточно двойного клика; ручной PowerShell/Git/pip не нужен.

## Этап 5. Снижение технического долга без изменения поведения

### Цель

Сделать код предсказуемым для дальнейшего сопровождения.

### Задачи

#### MR-0501. Mypy strict

Снижать baseline по модулям в порядке риска:

1. `core/domain`;
2. финансовые services/logic;
3. export/reconciliation/rsch;
4. ingestion/discovery;
5. app controller/bootstrap;
6. UI.

Правила:

- запрещены массовые `Any`, `cast` и `# type: ignore` без объяснения;

- сначала типизировать внешние границы, затем внутренности;
- после каждого модуля запускать golden-набор.

Итоговая цель — 0 ошибок `mypy --strict` для `APP`, либо документированный минимальный список ошибок сторонних библиотек, исключённых точечно.

#### MR-0502. Ruff и структура

- Сохранять текущий clean E/F.

- Удалить реально мёртвый код только после подтверждения поиском, тестами и runtime entry points.

#### MR-0503. Границы архитектуры

- UI не должен содержать финансовые расчёты.
- Domain не зависит от Tkinter, openpyxl и файловой системы.
- Infrastructure реализует интерфейсы domain/services.
- AppController координирует, но не дублирует расчёты.
- Устранение циклических импортов выполнять малыми шагами.

### Gate этапа 5

- Golden-набор неизменен.
- 0 новых mypy/ruff ошибок.
- Целевой strict mypy достигнут либо остаток документирован и согласован.
- Все удалённые элементы доказанно не использовались.

| Этапы 5–6: типы, тесты, покрытие | 8–15 дней |
| Этапы 7–9: Windows UX, performance, recovery | 7–12 дней |
| Этапы 10–11: документы, rehearsal, исправления | 4–7 дней |
| Пилот | 5–10 рабочих дней календарного наблюдения |

Итого без защиты: ориентировочно **35–50 рабочих дней инженерной работы плюс пилот**. Срок может сократиться, если часть текущих UI-чеков и документации подтвердится без исправлений. Он не должен искусственно сокращаться за счёт пропуска golden, rollback или Windows-приёмки.

> ⚠ Реалистичный диапазон с учётом скрытых объёмов (mypy strict на финансовой логике, починка дрейфа UI-тестов, разрешение Q1 про содержимое `versions/`): **45–60 рабочих дней + пилот**. Заказчику следует озвучивать верхнюю границу, чтобы дедлайн не стал нарушением.
