## 1. Методология и стандарты

### 1.1 Цель тест-плана

Доказать, что **Master-Report Consolidator v5.6 готов к передаче заказчику**:
100% функциональности проверено, поведение соответствует спецификации,
визуальный слой не содержит регрессий, риски потери данных исключены.
Тест-план служит «proof качества» для продажи и единственным
авторитетным реестром пройденных проверок на момент релиза.

### 1.2 Уровни тестирования (Test Levels)

| Уровень | Где покрывается | Покрытие | Ответственный |
|---|---|---|---|
| **Unit** | `tests/test_*` (логика, расчёты, парсинг) | ~70% из 456 тестов | pytest (CI) |
| **Integration** | `tests/test_phase*`, `tests/test_qa_sweep_*` | сквозные сценарии парсер→логика→БД→экспорт | pytest (CI) |
| **Property-based** | `tests/test_qa_sweep_*` (через hypothesis runtime) | фаззинг числового парсинга | pytest (CI) |
| **Simulation** | `tests/simulation_runner.py`, `tests/simulation_runner_real.py` | нагрузочные прогоны на реальных данных | ручной запуск |
| **E2E (авт.)** | `tests/test_phase0_gui_marshaling.py` | marshall/queue между worker-потоком и Tk-main | pytest (CI) |
| **E2E (ручной)** | Раздел 3 этого документа | оконный chrome, тосты, темы, контекстные меню | QA-инженер |
| **Visual Regression** | Раздел 5 этого документа | baseline-скриншоты light/dark | QA-инженер |

> **Принцип разделения.** Автотесты проверяют *поведение логики* (что и почему
> происходит). Ручные UI-тесты проверяют *то, что видит пользователь* (как это
> выглядит и реагирует). Это не дублирование — обе оси необходимы: Tkinter/ttk
> визуальный слой не покрывается pytest на 100%.

### 1.3 Стандарты

- **IEEE 829-2008** — структура тест-плана (разделы, идентификаторы тест-кейсов
  `TC-XXX`, критерии pass/fail, отчётность).
- **BDD / Gherkin** — сценарии в формате `Функция / Сценарий / Дано-Когда-Тогда`
  (см. раздел 4). Declarative-стиль: бизнес-намерение, а не click-by-click.
- **Visual Regression Testing** — методология baseline + diff по аналогии с
  Applitools / Percy, реализованная вручную для Tkinter (раздел 5).
- **WCAG 2.1 AA** — контрасты проверяются автоматически в code-gate U6
  (`verify_gate.py`).

## 2. Запуск тестов (How-To)

> Все команды выполняются из корня репозитория `E:\Dlia Dashi\Version5`.
> Интерпретатор — всегда из `.venv`, чтобы гарантировать совпадение версий.

### 2.1 Unit + integration автотесты (ожидаемый результат: **456 passed**)

```bash
.venv/Scripts/python.exe -m pytest tests/ -q
```

Ожидаемый хвост вывода:

```
--------------------------------------------------
```

> Если в выводе появились `failed` или `error` — это **release blocker**.

```bash
.venv/Scripts/python.exe -m pytest tests/ \
  --cov=APP/core --cov-report=term-missing -q
```

`term-missing` показывает, какие строки никогда не выполнялись. Не должно быть
файлов с покрытием `< 60%` в `APP/core/domain/` и `APP/core/services/`.


  относительно baseline — release blocker.

`tests/golden/` и сохраняет JSON-отчёт. Используется в дополнение к pytest для
нагрузочной проверки перед релизом.

## 5. Visual Regression Testing

### 5.1 Концепция

Visual Regression Testing (VRT) — методология сравнения скриншотов UI с
эталоном (baseline). Любое незапланированное визуальное изменение (сдвиг layout,
изменение цвета, «поплывший» шрифт) помечается как diff и блокирует релиз.

В индустрии это реализуют инструменты **Applitools Eyes**, **Percy**, **Playwright
snapshot**. Tkinter-приложения не имеют готового коммерческого VRT-решения,
поэтому применяется **ручная baseline-методология**: захват эталонных скриншотов
+ визуальное сравнение при регрессии.

### 5.2 Процесс

1. **Baseline-захват** (один раз для версии 5.6):
   - Запустить приложение в светлой и тёмной теме при 100% DPI.
   - Сделать скриншот каждого контрольного экрана (см. 5.4).
   - Сохранить в `docs/superdoc/baselines/` с именем
     `<screen>_<theme>.png` (например `sidebar_light.png`).

2. **Регрессионная проверка** (перед каждым релизом):
   - Повторить захват при тех же условиях.
   - Сравнить попиксельно (например, через `PIL.ImageChops.difference` или
     Win-инструмент «Сравнить рядом»).
   - Если есть diff — завести баг с приложенным скриншотом-diff.

3. **Обновление baseline** (только при намеренном изменении дизайна):
   - Зафиксировать причину изменения (commit / ADR).
   - Переписать baseline-файл.
   - Пометить в `CHANGELOG` обновление baseline.

### 5.3 Чек-пойнты для каждого скриншота

| # | Чек-пойнт | Что проверяем |
