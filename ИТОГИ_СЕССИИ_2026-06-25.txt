1. УПРОЩЕНИЕ ПРАВИЛ СВЕРКИ (scoring-based matching)
─────────────────────────────────────────────────────────────

Вместо 7-уровневого каскадного сопоставления (exact → executor
mismatch → amount mismatch → weak customer → surname → ... → error)
внедрён единый scoring-алгоритм:

  Для каждой Master-строки:
    1. Найти RSCH-кандидатов с совпадающей суммой (±0.01₽)
    2. Оценить пару:
       - Совпадение исполнителя: max +50
       - Совпадение заказчика: max +50
       - Same-row бонус (Master N + RSCH N в одной строке): +30
    3. Отсортировать по баллу, жадное назначение (каждый RSCH — 1 раз)
    4. Статус: ≥90 → СВЕРЕНО, ≥40 → ПРОВЕРИТЬ, <40 → ОШИБКА

Удалён мёртвый код (~150 строк): _customer_exact_or_alias_match,
_find_best_rsch_match, _find_likely_*_mismatch, _surname_tokens,
_weak_customer_review_candidate_matches и др.

Причины расхождений возвращены через _pair_reason().

     СВЕРЕНО. Интегрирован в build_combined_reconciliation_report
     глобально по всем листам. Эффект: +91…100 строк из отчёта.

4. ИСПРАВЛЕНИЕ БАГА (token threshold)
─────────────────────────────────────────────────────────────

Проблема: _executor_matches отфильтровывал токены по len≥4.
Короткие исполнители: «сби» (3 символа), «вб» (2) — отсекались.
right_tokens становился пустым → функция возвращала False →
исполнитель не совпадал → всего ~45 баллов → ПРОВЕРИТЬ.

Исправление: порог снижен с 4 до 2.
Пример: {"сби"} ⊆ {"сби", "альфа"} → True → +50 баллов → 95 → СВЕРЕНО.
